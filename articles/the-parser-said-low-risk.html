The Parser Said Low Risk

2026-09-29 · dispatch

The chargeback report landed on a Monday morning: 340 disputed transactions from the previous Thursday through Sunday, against a normal weekend of about 40. The fraud ops lead pulled the scoring history for the disputed set. Every one of them had been scored low risk by the LLM classifier and auto-approved.

The classifier was a second-opinion layer. The rules engine flagged borderline transactions, and the model reviewed each one with the order context, then returned a JSON verdict: risk level, reasons, recommended action. It had been in production for five months and caught a meaningful share of what the rules alone missed.

The pipeline dashboard showed zero errors for the weekend. That was true, and it was the problem.

The scoring service called the model, then ran json.loads() on the response. If parsing failed, an except block logged a warning and returned a default verdict so the checkout flow wouldn't stall. The default was {"risk": "low"}. The developer who wrote it had a reasonable goal: never block a customer's purchase because of a parsing hiccup. It had fired a handful of times in five months.

Thursday afternoon, the provider shipped an update to the model behind the alias the team was using. The new version wrapped its JSON in a Markdown code fence. Every single response failed to parse.

The test suite didn't catch it, because the tests replayed recorded responses from the old version.

For 71 hours, every transaction the rules engine escalated went to the model, got a correct, carefully reasoned answer, often “high”, and then had that answer thrown away and replaced with “low.” The model was working better than ever. The pipeline was approving everything.

“The model was working better than ever. The pipeline was approving everything.”

Nothing alerted, because nothing errored. The parse warnings went to a log stream with no alert attached. The distribution of verdicts shifted from about 91% low to exactly 100% low, and nobody was watching the distribution.

The fix to the parser was one line: strip code fences before parsing. The real fixes were about failure direction. A parse failure now fails closed: the transaction goes to the manual review queue, which is slower but safe. The team switched to the provider's structured-output mode with a strict schema, so malformed output becomes an API error instead of a string to interpret. The model version is pinned. And there is now an alert on the verdict distribution itself. Any class going to 0% or 100% for more than 15 minutes pages someone, because a classifier that only ever says one thing has stopped classifying.

The chargebacks cost about $61,000. The bigger cost was learning that a safety system had a default that turned it off.

When your parser can't read the model's answer, the default you pick is the answer. Choose it like one.
