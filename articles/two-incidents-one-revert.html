Two incidents, one revert

2025-04-22 · dispatch

The quality alert came in at 3:17 AM. The team had rolled model v2.8 to production six hours earlier, and automated evaluation was flagging a 12% drop in answer relevance. The on-call engineer confirmed it — v2.8's outputs were measurably worse. The decision took ninety seconds: roll back to v2.7, the last known-good version.

The rollback completed at 3:34 AM. The quality alert cleared. For four minutes, everything looked fixed.

Then the search-alert fired. Every RAG query was returning zero results. Not degraded results — zero. The retrieval pipeline was hard-failing with dimension-mismatch errors from the vector database.

Here's what the rollback hadn't accounted for: during the six hours v2.8 ran in production, it had been writing embeddings to the vector store using its 1536-dimensional output space. The previous model, v2.7, used 768 dimensions. The rollback restored the model to v2.7, but it didn't touch the vectors v2.8 had already written. Now v2.7 was trying to compute cosine similarity between 768-dimensional query vectors and 1536-dimensional document vectors. Every single comparison failed.

The on-call engineer had two options, both bad. Roll forward to v2.8 again — but v2.8 still had the quality problem that triggered the rollback in the first place. Stay on v2.7 — but search was completely broken, which was worse than degraded quality. She was stuck between the original incident and a new one the revert had created.

"She was stuck between the original incident and a new one the revert had created."

The third path took forty minutes to find: re-index the affected vectors using v2.7's embedding model, then run a backfill from the source documents. It worked, but it meant ~340,000 documents re-embedded at 3 AM while the team held their breath watching error rates. The full recovery took 67 minutes. The original quality incident had lasted six hours. The rollback incident added another 67 minutes of total search outage on top.

Nobody had tested the rollback path against the current state of the vector store. The rollback procedure assumed the system would look the same as it did when v2.7 was last in production. It didn't. The new model had mutated the data layer in a way the old model couldn't read, and the rollback script had no step for that.

What this left behind: a rollback is not a time machine — it rewinds code, not data, and any data the newer version wrote in a format the older version can't parse becomes an instant second incident. Rollback safety for AI systems requires a compatibility check against the current data state, not just a version revert; if your embedding dimensions changed, rolling back the model without re-indexing is a loaded gun. And the moment you realize the revert made things worse, you're in the worst position on-call: you can't go forward, you can't stay back, and you need a creative third path that nobody scripted at 3 AM.

"The rollback fixed the alert. Then the rollback became the incident."
