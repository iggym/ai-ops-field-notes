When Green Means Dead

2025-01-05 · dispatch

At 03:47 UTC, every dashboard for the chat assistant glowed a comfortable green. CPU normal. p95 latency 412 milliseconds. Error rate 0.02%. In a community Discord, a user posted: “It just told me it can't access its own memory.” Forty-six minutes later, the same user posted again: “Now it's just 500s.”

The status page acknowledged nothing for another twenty-eight minutes.

The first forty-six minutes are the part worth studying. The server was up. Requests returned 200 OK. Responses were valid JSON with the right model name in the envelope. They were also wrong: stale, stripped of the conversation's context, or quietly empty. Every metric an SRE is trained to alert on stayed flat, because none of them measured whether the answer was correct.

This is the modern shape of an AI incident. The system isn't down. The system is wrong. And the monitoring was built to detect the first.

December 2024 had a run of these in public. Users of AI coding tools posted threads about getting the same answer to different prompts, and those threads collected hundreds of upvotes before any status page moved. Chat assistant users reported forgotten context well before outages were acknowledged. In each case the first signal came from outside: a Reddit thread, a Discord channel, a spike in searches for “is it down.”

The mechanism behind this pattern is mundane. A caching or session layer sits between the user and the model. A response cache keyed too loosely on prompt similarity starts serving one user's completion to another user's question. A session-state store loses sync during a routine migration, and the model starts answering without the history it was promised. Either way, the layer serves responses that pass every structural check.

⚠ Known prompt, known answer. The cached response passed every transport check and failed the only one that asks whether the answer is right.

And the dashboards reward it. A high cache hit rate looks like a win. Nobody had instrumented the only question that mattered: is this cached response valid for this prompt? User-side symptoms are too vague to threshold. “The model seems off today” doesn't show up in an error budget. It shows up as a Reddit post.

The blast radius grows quietly too. Because the outputs are valid HTTP and valid tokens, downstream agents keep consuming them. Autonomous agents feed stale tool outputs into their reasoning loops, retry, and consume more. The first honest internal signal is often a billing spike. Observability arrives third.

“The system isn't down. The system is wrong.”

The fix is not exotic. If your system has a cache or session layer in front of a model, run a semantic canary: a fixed prompt with a known answer, on a schedule, asserting a substring match plus an embedding similarity above 0.85, wired into the same pager as your 5xx alerts. It's about twelve lines of code, and it is the one alert that fires on the failure class your dashboards are structurally blind to.

“Is the server up?” and “is the model answering correctly?” used to be the same question. They have stopped being the same question. Write the canary before your next on-call shift. The next invisible incident is already on its way. Don't read about it on Hacker News first.

In LLM systems, the 200 OK is the lie. Your monitoring watches the transport contract while the real contract is semantic.
