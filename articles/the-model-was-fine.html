Green alerts, silent RAG

2025-02-17 · dispatch

The page came in at 2:14 AM, but not from any alert. The on-call engineer was already awake — a Slack message from the content team in Singapore: "Search is returning completely irrelevant results. Has been for about an hour."

He pulled up the dashboard. Every metric was green. OpenAI API p99: 187ms. Error rate: 0.3%. Uptime: 99.97%. He checked the RAG pipeline logs. Retrieval step completing in under 200ms. Nothing timing out. Nothing erroring.

He ran a test query himself. "Find me Q4 planning docs about the Austria expansion." Top result: an onboarding guide from 2022. Something was deeply wrong, and no alert had fired.

Forty-two minutes earlier, OpenAI's embeddings endpoint had started returning 503s. Not the chat completions endpoint — that was fine, which is why the headline API metrics looked healthy. The team's monitoring watched chat completion latency and error rate as a proxy for "OpenAI health," because when they'd wired up the provider, they'd treated it as one dependency. One API key. One billing account. One box on the architecture diagram.

Their system actually depended on three separate OpenAI services: chat completions for generation, the embeddings endpoint for vectorization, the moderation endpoint for output filtering. Each with its own failure mode, its own rate limits, its own capacity profile. The diagram showed one box.

The RAG pipeline's error handling made things worse. When embeddings 503'd, retrieval caught the error and fell back to a cached embedding — but the cache had been populated days earlier with vectors from a different model version. The cosine similarities were off just enough to return results that looked plausible but weren't. No hard error. No empty result set that would've triggered a keyword search fallback. Just confidently wrong answers, served fast.

"Just confidently wrong answers, served fast."

A content manager in Singapore noticed because she searched for something she'd written that morning and it didn't appear. That's what caught it — a human running a specific, verifiable query. Not any monitoring system.

The fix took eleven minutes: route embeddings through a separate circuit breaker with its own alert threshold, add a stale-cache detection flag, switch the RAG fallback to keyword search on provider error. The incident lasted 53 minutes. The monitoring gap had existed for four months.

What they hadn't known: that "OpenAI" on the architecture diagram was actually three services, each with its own failure mode — and watching one endpoint as a health proxy for all three is a bet that outages are always total. That stale cached embeddings are more dangerous than empty results, because no results triggers a fallback but wrong results sails through. And that infra alerts on latency and error rate cannot catch a relevance problem. You need a canary query with a known answer, and you need it to scream when the answer changes even if the response time doesn't.

"The page that caught this came from a person, not a pager. The pager was green."
