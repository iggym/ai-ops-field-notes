The Commit That Never Happened

2026-01-14 · dispatch

The page came in at 02:14 AM.

The primary extraction worker was dumping thousands of unhandled exceptions into Sentry. SyntaxError: Unexpected end of JSON input. The pipeline had ingested 12,000 incoming vendor invoices over the last hour and failed on every single one.

The on-call engineer checked GitHub immediately. No deployments had gone out since Tuesday afternoon. The main branch was clean. The staging environment was quiet. Yet every single invoice parsing job was failing at the exact same step: validating the structured JSON payload returned from the model API.

By 03:00 AM, the incident response channel was filled with theories. Someone suggested a database lock. Someone else blamed corrupted PDF uploads from an upstream vendor. The team spent ninety minutes inspecting invoice file encodings, diffing database migrations, and restarting worker pods. Nothing changed. The parser kept receiving broken, half-written JSON strings.

Then someone printed the raw HTTP response body from the provider.

⚠ The alias model-v2-latest flipped at midnight UTC. The new model spent ~400 extra tokens before the JSON and hit max_tokens=1024. The API stopped mid-array and still returned 200.

The API was returning HTTP 200 OK. The latency looked normal. But the tail end of the response body stopped abruptly in the middle of an array.

The code wasn't crashing because of an invalid document. It was crashing because the response was cut in half.

Two weeks earlier, the team configured their API requests using the provider's rolling model alias, model-v2-latest, instead of pinning a specific dated checkpoint. At midnight UTC, the provider quietly flipped that alias to a new model iteration. The new model was smarter, but it was also significantly more verbose. It spent 400 extra tokens explaining its reasoning inside internal fields before outputting the final JSON schema.

“Because the client code checked the HTTP status code instead of finish_reason, it passed the half-baked string straight to the JSON parser.”

That extra verbosity pushed the overall output length past the client's hardcoded limit of 1,024 tokens. The API didn't throw an error when it hit the limit. It simply stopped generating text, set finish_reason: "length", and returned a 200 OK with a truncated string.

The fix took two minutes: bump max_tokens to 4,096 and pin the request to the exact dated snapshot model-v2-2025-11-01. The cleanup took five hours. Twelve thousand invoices had to be re-processed through the queue before the morning finance run.

“Floating model aliases are unversioned dependencies running third-party code in your production path.”

When you build on top of external AI models, your system code isn't just what lives in your repository. If you don't pin the exact model checkpoint and validate completion reasons, an upstream release notes item will eventually become your 2:00 AM postmortem.
